## 1. ★ 真正的 cJSON 解析器 = **0x203E2F8**

### 1.1 功能特征逐条命中（不是猜）
```
0203e2f8: [--sp] = {rets, r15-r4}      ; 入口
0203e2fa: sp += -44
0203e2fc: r8 = r0                      ; ★ 入参 = const char*（JSON 文本）
0203e2fe: r0 = 1
0203e300: r1 = 48
0203e302: call malloc(1,48)            ; ★ 节点 48 字节(0x30)
0203e308: r4 = r0
0203e30c: if (r4 == 0) goto ...        ; 失败返回 0
0203e312/318: call malloc(32,20)       ; 第二块结构
0203e326: call 0x203DF64               ; 解析器初始化 A
0203e330: call 0x203DFE8               ; 解析器初始化 B
0203e344: call strlen(r8)              ; ★ strlen(输入)
0203e34a: ...
0203e370: r0 = b[r8+0]                 ; ★ 逐字符处理起点
0203e378: goto 0x203EA70               ; ★ 大 switch（字符分派）
```
- 字符比较特征（L2/L4 扫描统计）：`"` `{` `}` `[` `]` `:` `,` + `t/f/n/u/r/e/l`
  共 10 种不同字符比较，总 15 处 —— 与 cJSON `parse_value` 的
  `"null"/"true"/"false"/字符串/数组/对象/数字` 分支完全对应
- 它**只有一个直接调用者**（见 §2），且该调用者把**拼好的 JSON 文本**传进来（sprintf 之后），
  返回值当树用（后续 `call 0x203F7C4` 取字段）

### 1.2 入口前 6 字节（hook 覆盖用）
```
文件偏移 0x03E1F8:  7f 04 e2 95 08 16
```
解码：`7f 04` = `[--sp] = {rets, r15-r4}`；`e2 95` = `sp += -44`；`08 16` = `r8 = r0`
→ 用 `80 ff <rel32>`（6 字节长调用）覆盖后，stub 里**重放这 3 条指令**再跳回 `0x203E2FE` 即可。

### 1.3 对比：为什么 0x200843A 不是它（支持你的实测结论）
- 0x200843A/0x20083B6 的体内是 `strlen → malloc → 3 字节魔数比较(0x20E7CF0) → fopen(0x2007E1A) → get_system_enc_key(0x2008148)`
  = **syscfg 文件读取/解密**，与 JSON 无关 —— 与你 hook 后 MQTT 无效的现象一致
- 我上一轮"它是 JSON 解析器"的依据（分发器 0x201B9F4 调它并在失败时打 `pMsg cJSON_Parse fail`）
  只能说明**分发器自己也用这个"通用 buffer 加载器"**，它内部会分派 syscfg/json 两种格式；
  这条路并非 MQTT 路径 → 结论作废，接受你的实测判定

## 2. 解析调用点 + 调用者（风险评估）

| 项 | 值 |
|---|---|
| **解析器** | `0x203E2F8` |
| **唯一直接调用点** | `0x203FB52`（短调用 `bf ea`） |
| 所在函数 | `0x203F8CE`（**云协议二进制帧处理器**） |

### 2.1 调用点上下文（关键！）
```
0203f8d6: if (r1 == 6) goto ...        ; 帧类型
0203f8da: if (r1 != 9) goto ...        ; 其它类型
0203f8f8: r0 = b[r5+0] (u)             ; 帧字节
0203f900: if (r0 == 160) goto 0x203F934 ; ★ 魔数 0xA0
0203f904: if (r0 != 176) goto ...        ; 0xB0
0203f90a: b[r5+1] == 1
0203f912: b[r5+2] == 0
0203f91a: b[r5+3] == 0
0203f922: b[r5+4] == 79                  ; 0x4F
...
0203fb44: r1 = 256                        ; sprintf(buf,256, fmt, arg)
0203fb4c: call sprintf
0203fb50: r0 = r6                         ; buf
0203fb52: call 0x203E2F8                  ; ★ JSON 解析
0203fb58: if (r4 == 0) goto error         ; 解析失败
0203fb5a: call 0x203F7C4                  ; 从树里取字段
```

**⟹ 这个云模块的消息帧是二进制头 `A0 01 00 00 4F ...`，JSON 是帧内负载。**

### 2.2 风险评估：**低**
- 0x203E2F8 的直接调用者**只有 1 个**（0x203FB52），且该调用点在**云协议帧处理器**里
- 不是启动早期被大量调用的通用函数 → hook 不会影响开机（与你测试 A/B 的经验一致）
- 0x203F8CE 自身没有直接调用者（由任务/表驱动）→ 说明它只在网络消息到来时执行

## 3. 给你的实测方案（最快验证）

### 方案 1（推荐）：hook 解析器 0x203E2F8
- 覆盖 `file_off 0x03E1F8` 6 字节：`7f 04 e2 95 08 16` → `80 ff <rel32>`，
  `rel32 = stub - (0x203E2F8 + 6) = stub - 0x203E2FE`
- stub 里：重放 `[--sp]={rets,r15-r4}; sp+=-44; r8=r0`，然后
  `strstr(r0,"@ALARM")` 命中 → 处理；否则 `jmp 0x203E2FE` 继续原解析
- 若设备上电正常、且发 MQTT 后 stub 被调用 → 这条就是 MQTT/云消息的真实解析路径

### 方案 2：用二进制帧格式再发一次 MQTT（很可能就是之前失败的原因）
此前你发的都是**裸 JSON**。若 MQTT 负载也要走云协议帧，则应发：
```
A0 01 00 00 4F ... <JSON 文本>
```
（`0xA0 0x01 0x00 0x00 0x4F` 是帧头前 5 字节；后面长度/序号字段未完全解出，
建议先用 `A0 01 00 00 4F` + `<JSON>` 试，或抓一次设备**自己发出去**的帧做模板）

### 方案 3：若方案 1 未命中
说明 MQTT 走的是**另一套解析**（未定位）。此时：
- 抓设备自己发出的 MQTT payload（它能正常发 publish）→ 按其格式回灌
- 或退回到"用 JSON 解析器 hook + 帧格式"的组合再试

## 4. 诚实标注
1. **MQTT 收包回调仍未定位**：MQTT 库回调是结构体成员指针；`MQTTSubscribe failed` 串恰在池基址
   0x2186540（163 处引用均为"池基址加载"），无法唯一定位到某个 log 调用点。
2. 本轮的 0x203E2F8 是**按功能特征**（入参 char*、malloc(1,48)、strlen、字符 switch、t/f/n 比较、
   返回树指针 + 后续取字段调用）在 735,630 条全量反汇编里筛出来的唯一强候选；其它候选
   （0x214EBAA、0x210F662 等）经验证是**数据区误解码**，排除。
3. 0x203F8CE 的帧头只解出前 5 字节（A0 01 00 00 4F），长度/序号/校验字段未解；建议抓设备发出的帧对齐。

## 5. 一句话结论
- **真正的 JSON 解析器 = 0x203E2F8**（文件偏移 0x03E1F8，前 6 字节 `7f 04 e2 95 08 16`）
- 它只有 **1 个调用点 0x203FB52**，位于云协议帧处理器 0x203F8CE（帧头 `A0 01 00 00 4F`）→ **hook 风险低**
- 之前 MQTT 无效可能不只是 hook 位置问题，而是**负载格式**问题（云协议是二进制帧 + 帧内 JSON），建议同时试方案 2
