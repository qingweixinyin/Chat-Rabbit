## 1. 必答 1：0x203F8CE 的注册点与调用链

### 1.1 它不是被 `call` 调用的，而是**注册成函数指针**
va **0x21DF154..0x21DF162** 处的初始化代码（模块上下文结构体 r3）：
```
21df14c: r0 = 0x20E8D2C
21df152: [r3+16] = r0        ; 回调 +16
21df154: r0 = 0x203DD82
21df15a: [r3+20] = r0        ; 回调 +20
21df15c: r0 = 0x203F8CE      ; ★ 帧处理器
21df162: [r3+24] = r0        ; 回调 +24
...
21df136: r0 = 0x21DF556
21df13c: [r3+4]  = r0        ; 数据段指针
21df16c: r0 = 0x40A7310 ; r1 = 0x203FC7E ; [r0+52] = r1   ; 另一个全局注册
```
- 该结构体属于**云协议模块**（同区还有 0x203DD82 / 0x203FC7E 等）；`r3` 由上层在模块初始化时给出
- 该模块的初始化由任务/表驱动（`0x203F8CE` 本身 0 个直接调用者，u32 指针仅 1 处即上面这条）

### 1.2 入参形式（决定"帧从哪来"）
```
0203f8ce: [--sp] = {rets, r8-r4} ; sp += -292
0203f8d2: r5 = [sp+316]     ; ★ 帧缓冲指针（栈传参，第 N 个栈参数）
0203f8d6: if (r1 == 6) ...  ; r1 = 消息类型：6 / 9
0203f934: r0 = [sp+320]     ; ★ 帧总长度（栈传参）
```
⟹ 调用者是"**收包分发器**"：`(type, buf, len)` 中 `buf/len` 走栈（第 316/320 字节处的栈槽）。
本固件里没有任何直接 `call 0x203F8CE`；它与 `0x203DD82`、`0x20E8D2C` 一起挂在
**同一模块的回调表**上，由该模块的收包循环按类型派发。

**结论（保守但明确）**：这是**云协议模块**的"帧处理"回调，服务于**socket/云协议通道**
（与本项目已确认的 `smartdevice.ai.turingapi.com:80` / iTROS 通道同族）。
**没有证据表明 MQTT 消息会进这里**（MQTT 回调是另一套）。

## 2. 必答 2：完整帧格式（从 0x203F8CE 反汇编逐字节推出）

### 2.1 帧结构（type==6 分支，0x203F8F8 起）
| 偏移 | 内容 | 校验/说明 |
|---|---|---|
| +0 | **帧类型** `0xA0`(160)=数据帧 / `0xB0`(176)=应答帧 | 0xA0 进数据处理；0xB0 走应答分支 |
| +1 | **子类型/分片号**：`1` / `2` / `3` / `4` / `129`(0x81) | 1/2/3/4 = 数据分片；129 = ack/状态 |
| +2 | 序号 A | 与 +3 相等 ⇒ **本帧是最后一片**（置对应 bit） |
| +3 | 序号 B | 同上 |
| +4 | **本帧 payload 长度** | 0 合法（空片） |
| +5 .. +5+len-1 | **payload 原始字节** | 逐片拼进上下文缓冲 |
| 最后 1 字节 | **校验和** | `(sum(帧内前面所有字节) + 校验字节) & 0xFF == 0` |

校验实现（0x203F934..0x203F958）：
```
r2 = len - 1                  ; 遍历字节数
r0 = 0; for (i=0;i<r2;i++) r0 += buf[i]
r1 = buf[len-1]; r1 = -r1
if ((r0 & 0xFF) != (r1 & 0xFF)) → 丢弃整帧
```
⟹ **帧长度 = 4 + 1 + len + 1 = len + 6**（buf[0..len+5]），
   末尾校验 = `(0x100 - (前面所有字节之和 & 0xFF)) & 0xFF`。

### 2.2 分片语义（重要：**JSON 不在帧里**）
子类型 1 / 2 / 3 / 4 分别把 payload 追加到上下文的 **4 个独立缓冲**：
| 子类型 | 目标缓冲 | 单缓冲上限 |
|---|---|---|
| 1 | ctx + 5776 | 95 字节 |
| 2 | ctx + 9476 | 191 字节 |
| 3 | ctx + 2356 | 31 字节 |
| 4 | 同 ctx+19 累加 | 95 字节 |
拼完后 `ctx[+15]` 的 bit0/1/2 依次置位，全置位（==7）→ 触发"提交"流程
（0x203FB16 起：`0x2033650` 预处理 → 0x203DE00 处理两块缓冲 → **sprintf 拼串** → `call 0x203E2F8`）。

### 2.3 关于 `0x203FB52` 处的 `call 0x203E2F8`
```
0203fb38: r0 = 16055; r2 = r8 + r0     ; r8 = 0x217E530 池基址 → 格式串
0203fb44: r1 = 256; r0 = r6 (sp+7)
0203fb4c: call sprintf(buf, 256, fmt, ...)   ; ★ 本地拼 JSON
0203fb50: r0 = r6
0203fb52: call 0x203E2F8                      ; 解析"自己拼的" JSON
```
⟹ **0x203E2F8 在这里解析的是本机 sprintf 生成的 JSON，不是网络 payload**。
所以**hook 0x203E2F8 也抓不到 MQTT 下行 payload**（除非 MQTT 路径也调它，目前无证据）。

### 2.4 一条"最小合法下行帧"样例（按上面规则构造）
以 payload = `{"opt_code":"alarm_del","payload":{"alarmId":0}}`（48 字节）为例：
- payload 长度 len = 0x30
- 帧 = `A0 01 01 01 30` + payload(48B) + checksum(1B)
- 前缀 5 字节和 = 0xA0+0x01+0x01+0x01+0x30 = 0xD3
- payload 字节和 = 下面算
- checksum = (0x100 - (total & 0xFF)) & 0xFF

（具体 hex 见 §4 生成脚本输出；`make_frame.py` 已提供，改 payload 即可）

> 注意：上面是**按反汇编推出的格式**。真实设备能否接受，取决于：
> ① 该通道是否由 TCP 会话驱动（几乎确定）；② 分片要凑齐 4 个缓冲才提交（可能需要多发几帧）。

## 3. 必答 3：MQTT payload → 0x203F8CE **有没有路径？**

**结论：没有证据支持，判断为"不走这条路"。**
- 0x203F8CE 是云协议模块的**回调表成员**（`[ctx+24]`），入参走栈（buf/len），与 MQTT 的回调签名无关
- MQTT 收到消息后走的是 MQTT 库 → 应用回调（另一套，未定位）
- 因此：**把 A0/B0 帧当 MQTT payload 发出去，不会进 0x203F8CE**

⟹ 对补丁方案的影响：
1. **想靠 MQTT 下发，必须 hook MQTT 路径上的函数**（仍未定位）
2. **0x203F8CE 这条帧通道只能走 TCP（smartdevice/iTROS）**，而该会话设备从不建立 → 这条路对"不拆机"没帮助
3. `0x203E2F8` 只解析本机拼的 JSON → hook 它也无效（我上一轮的推荐需修正）

## 5. 诚实结论
- 帧格式已解（§2.1），**但帧里没有 JSON**——payload 是二进制分片，JSON 是设备自己拼的
- **MQTT 与这条帧通道互不相通** ⟹ 想用 MQTT 控制闹钟，必须另找 MQTT 回调/解析入口
- 在找到 MQTT 入口之前，**OTA/341A + 本地（BES 明文区）打补丁**仍是最可靠的两条路
