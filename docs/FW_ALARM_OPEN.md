## 已确证（不要再怀疑，也不要重新试）

| 事实 | 证据来源 |
|---|---|
| 闹钟写入 = MQTT 下行 `optCode=1003`，`optValue.hb[]` **整表替换** | 反汇编 `0x20389BE` + 实测 07:00/18:30/08:15 三条下发成功并持久化 |
| 记录字段：`na 名称 / th 时 / tm 分 / sd 起始秒 / wk 星期掩码 / wt 未知 / s 使能` | 设备 VM 区 `flash 0x7BF000` 实际内容 + 反汇编解析器 `0x200CCA6` |
| 整表下发寄存器链路：`0x2038DFA`(MQTT cb) → `0x2038802`(cJSON) → 跳转表 `0x2038876` → `0x200CCA6`(解析 hb) → `0x200722A`(BES 保存) | 反汇编交叉验证 |
| `wk` 位语义：bit0=周一 … bit6=周日；`63` = 每天；**`wk=0` 设备永不触发**（等于一天都没选） | 实测：wk=31 只周一到周五触发；wk=96 周末；v1.4.7 用 wk=0 写"仅一次"→ 15:37 的闹钟到点没响（App 与网页同样哑火） |
| 「仅一次」正确编码 = `sd`=目标日期 + **`wk`=该日期所在星期的单个位**（周四→8），响过后服务端自动删表（janitor，30 分钟后） | v1.4.8 实测：明天(10-29 周四)→ wk=8；过期条目 60s 内被 janitor 删除 |
| 音频播放 = MQTT `type:1 operate:1`，`mediaId` **必须与上次不同**才会播 | SDK `lib/net/turing/turing_mqtt_cmd.c: mqtt_message_audio()` |
| 播放 URL 不能带端口（`http://IP/media/x.mp3`），设备用 80 → iptables 重定向到 28081 | 实测 `MEDIA LOG` 出现 `GET /media/...` |
| 音量 = MQTT `type:2 operate:1 arg=N`，N 合法 **0~4**（越界会让设备重启） | SDK `mqtt_message_control()` + 实测 arg=8 导致设备重启 |
| 时间同步 = `GET /api/ntp.form` 返回**纯文本 10 位秒**；设备是 32 位时间，毫秒会溢出成 2037 年 | 实测 2037→2070→正确 的收敛过程 |
| 设备→服务端 心跳/状态 = `POST /iot/status/notify`，body `{type,status:{vol,battery,play,...}}` | 代码 `main.go` 解析点 + 实测 |

## 未决项（需要继续挖，别写结论）

### #1 `wt` 字段究竟是什么？（最高优先级）
- 现状：所有实测都写 `wt:0`，从未验证 1/2/3 的含义
- **2026-10-29 静态进展（已确证）**：
  - 闹钟记录解析器 `0x200CCA6` 明确把 `wt` 存到节点 **+16** 偏移（键池 `0x217e542`，`+102` = "wt"）
  - 节点布局：`+0=th、+4=tm、+8=sd、+12=wk、+16=wt、+20=s、+24=名称缓冲`
  - 序列化函数（引用链表头 `0x40253C4` 的那批函数，如 `0x2005896`）会把 `wt` 一并写回 VM JSON → **设备是持久化它的，不是丢弃**
  - 固件里还发现**第二套更完整的闹钟命令族**（字符串区 `0x217fa00~0x217fb95`）：
    `alarm_set` / `alarm_del` / `alarmType` / `cycleType` / `startDate` / `index_day` / `date2week`
    → 说明厂商还有一条"结构化闹钟"通道；`wt` 很可能对应其中的 `alarmType`（闹钟类型：普通/起床/吃药/生日…）
- 猜测优先级：
  1. `wt` = **闹钟类型 alarmType**（影响响铃方式/提示音/是否需要确认）
  2. `wt` = 铃声/音效编号（设备内置 prompt 索引）
  3. `wt` = 响铃时长档位
- 验证路径（进行中）：
  1. ~~反汇编解析器~~（已完成：+16 偏移确认）
  2. **实测矩阵**：给"2 分钟后"的闹钟分别设 `wt=0/1/2/3`，观察
     - 是否仍来 `GET /media/xxx.mp3`（=仍用我们的铃声 → wt 与音频无关）
     - 是否改为设备本地提示音/滴滴声（=wt 选内置音效）
     - 是否有额外动作（语音提示"闹钟时间到"、需要按键确认等）
  3. 若命中"内置音效"假设 → 继续找消费 `[node+16]` 的播放函数（可用 prompt 索引表反查）
- **禁止**再把 `wt` 标成"未知/占位"就结束；每轮收尾必看这条

### #2 唤醒键（终止闹铃）是否会主动上报？走哪条通道？
- 已做：服务端已解析 `status.play==0` 与 MQTT 上行里的 `"play":0`，一旦看到就开闸门 + 补发停止
- 未证：**这台固件按键后到底上不上报**
- 验证路径：按键瞬间同时抓 `REQ LOG`（HTTP）+ `MQTT LOG`（上行 PUBLISH），确认是否出现 `play=0`
- 若不上报 → 只能靠 `ring_seconds` 兜底；也可尝试按键是否触发 WS 帧（看 `serve.log` 的 `[WS] frame`）

### #3 `optCode` 1001–1010 的完整语义表
- 现状：确认 1003=整表替换；其余只知范围存在（跳转表 `0x2038876`，`r7 = optCode-1001`）
- 待做：把跳转表 10 个目标函数全部反汇编，逐个写用途
- 可能收益：删除单条、查询列表、设置铃声 等更细粒度指令（能替代整表替换）

### #4 BES 保存格式（`0x200722A`）与 VM 区冗余/校验
- 现状：知道写到 flash `0x7BF000`，无 CRC/长度头，NULL 结尾 JSON
- 待做：确认写入时的双备份/磨损均衡策略，避免我们"整表替换"打坏结构
- 风险：低（实测多次写入未损坏）

### #5 设备能否主动上报既有闹钟列表？
- 现状：未观察到设备回传 `hb[]`；我们的本地表是"唯一真源"
- 若设备能回传 → 可以做"以设备为准"的双向同步，避免 App 本地表与设备漂移

### #6 闹铃响时的真实入口（WS / `/v2/iot/audio` / `/api/v2` 哪条为主）
- 现状：三条都会出现；`/v2/iot/audio` 是"下一首"，WS 是"问播什么"
- 待做：在设备响铃瞬间抓一次完整序列，确定**首选入口**，减少多路径竞争（当前靠闸门+时间窗兜底）

## 教训（为什么要有这个文件）
- 早期把「`operate=8` 未实现」当结论，导致连续两天告诉用户"闹钟必须刷固件/无法实现"，
  后来才发现真正的通道是 `optCode=1003`。**根因：把"没看懂"写成"没实现"。**
- `wt` 被标"未知"后再没回头看，而它很可能正是"每条闹钟自带铃声"的钥匙。
- 规矩：**逆向中任何未证的东西只进本文件，不进结论；每轮收尾必须回看本文件有没有能推进的项。**
