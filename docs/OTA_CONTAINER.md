## 1. 容器格式（已确定）

```
offset 0x00  ┌─ 段表（2 × 0x20 字节）
             │  entry[0] @0x00
             │  entry[1] @0x20
offset 0x40  └─ 负载（连续，原始 flash 形态字节）
```

### 每个段表项 0x20 字节

| 偏移 | 类型 | entry[0] 值 | entry[1] 值 | 含义 |
|---|---|---|---|---|
| +0x00 | u32 | `0x0E3D19FF` | `0x223255D7` | **sign/随机字段**（不是标准 CRC，见 §2） |
| +0x04 | u32 | `0x00000020` | `0x00000040` | **链表 next**：指向下一段表项；最后一项的 next = 负载起点（0x40） |
| +0x08 | u32 | `0x001EDA01` | `0x001ED9C1` | **size**：entry0 = 整包文件长度；entry1 = 负载长度（= 文件长度 − 0x40） |
| +0x0C | u32 | `0x0001FF03` | `0x0000FF02` | 类型/标志（低 16 位 0xFF03 / 0xFF02，高 16 位 1 / 0） |
| +0x10 | char[16] | `"update_data"` | `"app_core"` | 段名字（NUL 填充） |

- **段表项数**：本包 2 项（`update_data` + `app_core`）；结构上是链表，理论上可多于 2 段（next 链）
- **负载起点** = 最后一项的 `next`（本例 0x40）
- **负载长度** = 最后一项的 `size`（本例 0x1ED9C1）
- **无尾部校验**：文件末尾没有额外结构（长度已由 entry0.size 界定）
- entry0 是"整包描述"（size=整包长度），entry1 才是"真正的数据段"

### 负载基址（写入 flash 的绝对偏移）
- 生成镜像的负载（0x40 起）与 `jl_isd.bin[0x4000:]` **逐字节相同**（你已核对）
- ⟹ **负载 = 从 flash 0x4000 开始的连续字节**（不是 0x4020！包含 app 区目录前的 0x20 私有块）
- 长度 0x1ED9C1 → 覆盖 `0x4000 .. 0x1F19C1`

> 说明：镜像里 0x4000 是"生成镜像的 app 区起点"；对设备而言，`0x4000` 正好是
> `app 区头之前 0x20 字节`的位置。所以**只要负载取 `设备dump[0x4000:0x4000+len]`**，
> 写入后就是**设备原厂布局**（app 区目录仍在 0x4020）——这正是我们要的。

## 2. sign/CRC 字段结论（重要）

两个 4 字节字段 **都不是标准校验**：
- 试过：`crc32`（reflected，init 0/0xFFFFFFFF × xorout 0/0xFFFFFFFF）、`crc32`（non-reflected poly 0x04C11DB7）、
  `adler32`、简单 sum32，对 **负载 / 头 / 头+负载** 全部不匹配
- 与 JLFS 目录项首 u32 的现象一致（我在 §PATCH_INJECT 里也判定那不是标准 CRC）
- 最可能：isd_download 生成的**随机 sign / 每包 seed**（同一输入多次生成是否变化待验证），
  或使用厂商私有 CRC 实现（固件里有两张 CRC 表 0x2199108 / 0x2198D08，但都不是直接结果）

**对策**：`make_ota.py` 的做法是 **原样复用模板包的两个 sign 值**（因为负载长度不变）。
若设备校验这两个字段 → 会拒包（安全失败，不会砖）。若要彻底消除该风险，需要再反出校验算法（见 §5）。

## 3. A/B 双区问题 ★

### 事实
| 项 | 值 |
|---|---|
| app 区 A 头 | flash **0x4020**，解密得 `app_area_head`，load 0x2000120，size 0x1ED423 |
| app 区 B 头 | flash **0x3DB020**，解密得 `app_area_head`，load 0x2000120，size 0x1ED423 |
| 容器负载 | 只有 **1 段数据**（app_core，0x1ED9C1 ≈ 2 MB），覆盖 `0x4000..0x1F19C1` = **仅 A 区** |

### 结论（明确回答）
1. **这个 OTA（robot 接口触发的网络升级）是"单段原地写"** —— 容器里**没有任何 B 区段**
   （负载只有 2 MB，B 区在 0x3DB020，完全不在覆盖范围内）。
2. 因此 **不需要**在包里放两个槽；我们**只需替换 A 区内容**（payload 取 `dump_patched_code.bin[0x4000:0x1F19C1]`）。
3. 风险：如果升级后 bootloader 选择从 B 启动，补丁不生效（但设备正常，可用同法再发一次包，或 341A）。
   厂商自己的 OTA 包同样只带 A 区 ⟹ 其升级流程必然是"写 A 并标记 A 有效/从 A 启动"，否则它的
   OTA 也会"看起来没升级"。**因此我们的包沿用同样结构，行为与官方包一致。**

> 如果实测发现升级后没生效（怀疑切到 B），下一步可以做"B 区包"：把 payload 换成
> `dump[0x3DB000:...]` 并把 name 改成 `app_data`/`app_core2` 之类——但**这需要解析器源码/实测**，
> 当前无依据，不建议盲试。

## 4. make_ota.py（已交付并自测）

```powershell
cd "E:\Claude official\chat rabbit\work\ufw"
python make_ota.py ..\dump_patched_code.bin out\update-ota-patched.ufw
# 可选：--template out\update-ota.ufw  --payload-base 0x4000  --info
```
行为：
1. 解析模板包 → 2 个段表项 + 负载偏移/长度
2. **原样保留 0x00..0x40 的段表**（sign/type/name/next 不动，length 不变所以 size 仍正确）
3. 负载 = `dump_patched_code.bin[0x4000 : 0x4000+0x1ED9C1]`
4. 输出同结构包

自测：用 `_roundtrip.bin`（= 原厂 A 区明文重建的整片）生成包 → 长度 2,021,889、头部 0x40 与模板
**完全一致** ✓（内容不同是预期的：模板负载来自 SDK 镜像，我们的负载来自设备 dump）

## 5. 风险与恢复

| 风险 | 评估 |
|---|---|
| 段表 sign 字段被校验 | 中。被拒 → 升级失败但不砖（升级器一般在写入前校验；最坏情况写到一半掉电才砖） |
| 负载写到错误基址 | 低（沿用官方包结构，基址 0x4000 由包语义决定） |
| 升级后从 B 启动 | 低-中（官方包也只有一个段，行为应一致） |
| 砖机恢复 | **可以**：芯片是外置 SPI，`chat rabbit-puya.bin` 是全片备份，341A 可整片回写（你说 341A 明天可用） |

**建议执行顺序**：
1. 先用**未打补丁**的 `chat rabbit-puya.bin` 走一遍 `make_ota.py` 生成"原厂等价包"，
   发 OTA 验证"能否升级成功 + 升级后运行正常"（这一步验证的是容器格式/基址，不改行为）
2. 成功后再发**打补丁的包**
3. 若第 1 步失败（被拒/不生效），结论=OTA 容器还有未知校验 → 本次只能 341A

## 6. 仍未确定（诚实标注）
1. **OTA 容器解析器在固件里的位置**：全 app 明文里搜不到容器 magic `0e3d19ff`，也没有代码引用
   `"update_data"` 串（仅有池基址巧合引用）；uboot（13.7 KB）里也没有。
   推测解析器在 **`0x1F1443..0x2CC6B4` 这段我尚未识别的非 FF 区域**（可能是第二个 updater 镜像），
   或升级由 ROM/厂商私有流程处理 → 因此 §2 的校验问题只能靠实测确认
2. 段表 sign 的算法（同上）
3. 段类型字段 `0xFF03/0xFF02` 的语义（疑似 segment 序号/权限）

- 容器 = **2×0x20 段表（链表）+ 0x40 起的连续负载**；负载 = **flash 0x4000 起的原始字节**，长度 0x1ED9C1
- **只有 A 区一个段** ⟹ 单段原地写，**不需要双槽**；沿用结构替换负载即可
- `make_ota.py` 已就绪：`python make_ota.py ..\dump_patched_code.bin out\update-ota-patched.ufw`
- 唯一不确定是段表两个 4 字节 sign 是否校验 → **先发"原厂等价包"验证**，通过再发补丁包；砖了也能 341A 救回
